# Formshelf 実装プラン

作成日: 2026-09-13

状態: 本実装・代表検証・独立Final reviewを完了。実施内容は[検証記録](implementation-verification.md)を参照。

## 目的と最初の到達点

気に入ったUIを、見た目と操作感を持つコードとして集め、別の開発で再利用できるようにする。

まずは **実際のスクショまたはURLから1件を実装・保存し、Webアプリを起動せず、別プロジェクトのエージェントがMCPで検索・取得して移植できること** を目指す。その後、保存したUIを現在のギャラリーで閲覧できるようにつなぐ。

このファイルは作業順序と完了条件を整理する。合意済みの製品方針を変更するものではなく、保存形式やツール名などの実装案は、着手時に実物に照らして具体化する。

## 合意済みの前提

- 開発用PCで使う、個人用のWebアプリ。React＋TypeScriptのUIを中心に扱う。
- 部品と画面全体の両方を保存する。データはサンプルを使い、ホバー・開閉・切り替えなどの操作感を再現する。
- 入力はスクショまたはURL。URLだけなら対象部分を確認し、部分指定があればそのまま進める。
- リンク先を閲覧できない場合は、スクショや録画へ切り替える。
- 新しいUIの実装・登録は、このコレクションのプロジェクトで外部エージェントに依頼する。
- 別プロジェクトでは、完成済みUIを検索・取得して移植する。コレクション用の新規実装を混ぜない。
- 検索用の情報はSQLite、コード・画像はファイルに保存する。
- MCPは検索・取得専用とし、Webアプリから独立させる。
- Webアプリは見た目を確認するときだけ起動する。エージェント接続中にMCPプロセスが動くことは許容する。
- 一覧は白〜薄いグレーを基調に、サムネイルを主役にする。
- アプリ本体にキャッチコピーや装飾だけの英語は置かず、名前・説明・操作手順を直接表す文言にする。

根拠: [合意済みの設計判断](project-memory/records/20260913-051200-separate-collection-and-reuse.md)。

## 実装順序

### 0. モックのフィードバックを反映する

- [x] 一覧の情報量、文字の大きさ、サムネイル、詳細の使い勝手についてユーザーの確認結果を反映する。
- [x] 部品と画面全体の探し方、動くプレビュー、元画像、コードへの導線を整える。
- [x] 合意済みの収集・再利用フローに影響する変更があれば、このプランへ反映する。

完了条件: ユーザーが一覧から対象を探し、見た目と動きを確認できる。フィードバック待ちの箇所を、問題なしとして完了にしない。

### 1. 保存形式とSQLiteの土台を作る

- [x] UIごとに名前から生成しないUUIDの固定IDを割り当てる。既存項目の名前編集はまだ提供せず、内容を変えて新規登録した場合は別UIとして扱う。
- [x] Reactコンポーネント参照を含む現在の固定配列から、保存可能なメタデータを分離する。
- [x] SQLiteの初期スキーマと、バージョンを管理する移行処理を用意する。
- [x] コード、CSS、ローカル素材、参照画像を、UI単位の保存先へまとめる。
- [x] 登録処理・MCP・Webから同じコレクションを参照できる、作業ディレクトリに依存しない保存先設定を用意する。
- [x] 実データの保存先、Gitで管理する範囲、バックアップ対象を明示する。既存サンプルを黙って置換しない。

メタデータ案:

| 分類 | 保存する情報 |
| --- | --- |
| 識別・検索 | ID、名前、部品／画面全体、カテゴリ、タグ、特徴、気に入った点 |
| 参照元 | スクショ／URL等の入力種別、元URL（任意）、対象部分、参照画像の相対パス |
| 再利用 | TSX等の入口、ファイル一覧、必要な依存とバージョン、移植時の注意 |
| 表示 | サムネイル、実行用プレビューの入口、試せる操作 |
| 管理 | 作成日時、内容ハッシュ、登録完了を判別できる情報。既存データは更新しない |

画像・コード本文をDBへ重複保存しない。参照元の画像と、実装後のプレビューを撮影したサムネイルは区別する。

完了条件: 再起動後も1件のメタデータと全ファイルを取得できる。別の作業ディレクトリから同じIDを引ける。不正なID、保存先外へのパス、欠落ファイルを扱える。

### 2. コレクション側の実装・登録手順を作る

- [x] 外部エージェントが使うローカルの登録コマンドと、必要な入力形式を用意する。
- [x] スクショは原本を保存する。URLは対象部分を特定してから閲覧・撮影し、元URLと合わせて残す。
- [x] 閲覧できないURLから推測で再現せず、合意済みのスクショ／録画への切り替えを行う。
- [x] React＋TypeScriptで実装し、サンプルデータを使う。元プロジェクトのAPI、認証情報、私有ファイルを持ち込まない。
- [x] UI単位で移植可能にするため、現在の共有サンプルCSSへの依存を整理し、素材・CSS・依存情報の取り漏れを検出する。
- [x] 登録時にプレビューをビルドし、サムネイルを生成する。通常の検索・取得ではビルドやブラウザを起動しない。
- [x] 入力検証、ID重複、再実行、登録途中の失敗に対応する。既存UIを無条件で上書きしない。

登録の公開順序案: 一時領域でファイル検証とビルドを完了 → 完成したファイルを保存先へ配置 → SQLiteへ登録完了を反映する。DBとファイルを一括で原子的に更新できるとは扱わず、途中停止時の未登録ファイルや欠落を検出し、再実行・復旧できるようにする。

完了条件: 実際の参照素材から1件を登録し、元の作業ファイルへ依存せず取得・表示できる。不完全な登録は検索結果に出ず、失敗しても既存UIが壊れない。

### 3. 検索・取得専用MCPを作る

- [x] Webサーバーを必要としない、ローカルの `stdio` 接続のMCP入口を用意する。
- [x] 最初は名前・タグ・特徴・種類を使った文字検索にする。自然な依頼から検索語を選ぶ役割はエージェントが担う。
- [x] 検索結果はIDと短い説明を中心にし、件数上限を設ける。全UIのコードや画像を一度に返さない。
- [x] IDを指定すると、メタデータ、依存情報、ファイル一覧、必要なソース・素材を取得できるようにする。
- [x] 大きいファイルは分割取得や参照方式を使い、1回の取得量を制限する。ローカル素材も移植可能な取得方法を用意する。
- [x] 読み取り操作は保存先内の登録済みファイルに限定する。任意SQL、任意パス、コマンド実行を公開しない。
- [x] 接続例と、別プロジェクトから検索・取得する例を文書化する。

ツールの責務案（名前は実装時に確定）:

| 操作 | 入力 | 出力 |
| --- | --- | --- |
| `search_ui` | 検索語、種類／タグ、取得件数 | 候補のID、名前、特徴 |
| `get_ui` | 固定ID | 説明、依存情報、登録済みファイル一覧 |
| ファイル取得 | 固定ID、登録済みの相対パス | 対象のコード／素材。大きい場合は範囲や上限を明示 |

このMCPに登録・生成・移植先への自動書き込みを追加しない。選んだUIを移植先へ適用する仕事は、そのプロジェクトのエージェントが行う。

完了条件: Webサーバーとブラウザを停止した状態で、別プロジェクトから実際のMCPクライアントで検索・取得できる。DBやファイルが欠けていても、原因と対処が分かるエラーを返す。

### 4. ギャラリーを実データにつなぐ

- [x] Web側はローカルの読み取りAPIを通してSQLiteを参照し、固定配列を置き換える。ブラウザからSQLiteへ直接アクセスする前提にしない。
- [x] 保存領域を読む処理はMCPと共有し、Web側に検索・取得の別仕様を作らない。
- [x] 新規登録時にアプリのソースへ手でimportを追記せず、登録済みのプレビューを選べるようにする。
- [x] 一覧は静止画像、詳細は選択中の1件だけという現在の表示方式を維持する。
- [x] 元スクショ、参照URL、実装後サムネイルを適切に表示し、ソース・素材・依存情報を確認できるようにする。
- [x] DB未作成、0件、読み込み中、ファイル欠落、プレビューの失敗時の表示を追加する。
- [x] プレビューと保存APIの実行境界を設計する。現在の同一オリジンiframeを、未信頼コードを安全に実行する仕組みとして流用しない。

完了条件: 登録済みUIを一覧から開き、元画像・実装・コードを確認できる。プレビューを閉じれば実行が止まり、Webを止めてもMCPの取得が動く。

### 5. 実素材で一連の流れと運用を検証する

- [x] スクショ起点とURL起点をそれぞれ使い、保存から移植まで通す。
- [x] 部品と画面全体の両方で、移植先のスタイルと既存コードへの影響を確認する。
- [x] 参照元のURLが変わったり、元の作業ファイルがなくなったりしても、保存済みの実装・画像を使えることを確認する。
- [x] 同時登録・同時取得、再実行、異常終了、DBとファイルの不整合を検証する。
- [x] SQLiteとコード・画像をまとめた整合性のあるバックアップ／復元を用意し、別の保存先へ復元して取得できることを確認する。
- [x] 実際に使うブラウザで、キーボード操作、モバイル幅、プレビュー内からの閉じる操作を確認する。
- [x] 起動・停止、登録、MCP接続、バックアップ、失敗時の対処をREADMEへ反映する。

完了条件: 実データで「渡す → 実装・保存 → 探す → 取得 → 移植」を再現できる。モックの検証結果を、実DB・実MCPの動作確認の代わりにしない。

## 検証とメモリの確認方法

実装フェーズごとに、変更する外部挙動に対応した最小の検証を用意する。既存のレビューポリシー・テストポリシーを適用し、保存・復旧・MCPの契約には代表的な自動テストを持たせる。

| 対象 | 検出したい失敗 |
| --- | --- |
| 保存・登録 | データ消失、ID衝突、再実行時の重複、未完成UIの公開 |
| ファイル取得 | 保存先外の読取り、シンボリックリンクによる範囲外アクセス、素材の取り漏れ |
| MCP | Webへの依存、候補と取得内容の不一致、上限のない応答、接続・切断の不具合 |
| Web | 登録したUIが出ない、誤ったプレビュー、破棄漏れ、キーボード操作不能 |
| 復元 | DBだけ／ファイルだけが戻り、検索できても再利用できない状態 |

メモリは次の状態を同じ環境で比較し、プロセス数・RSS・子プロセスの残存を記録する。

1. このアプリとMCPが動いていない状態。
2. MCPに接続して待機している状態。
3. 検索・取得を繰り返したあとの状態。
4. Webの一覧表示中と、詳細1件のプレビュー表示中。
5. 詳細を閉じたあと、Web・MCPを終了したあと。

最初は実測値を報告し、許容するメモリの上限値は測定結果を見て決める。全件のソース常駐、一覧での全件実行、検索時のブラウザ／ビルド起動を避ける。プロセスが残らないことと、メモリ使用量が毎回ただちに開始前の値へ戻ることは区別する。
