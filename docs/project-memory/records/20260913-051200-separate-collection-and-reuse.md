# 収集と再利用を分け、閲覧用Webアプリの常駐を避ける

## Context

保存対象はスクショの一覧ではなく、他の開発へ移植できる実装済みUIである。UIを探すたびに閲覧用アプリを起動する負担と、PCのメモリ消費を避けたい。一方、別プロジェクトから収集・生成まで行うと、その開発作業にコレクション用UIの新規実装が混ざることをユーザーが懸念した。

## Decision

新規UIの収集・実装・登録は、このコレクションのプロジェクトで外部エージェントに依頼する。別プロジェクトには、検索・取得専用MCPから完成済みUIを提供し、そこで必要な移植を行う。保存はSQLiteのメタデータとコード・画像のファイルを組み合わせ、MCPは閲覧用Webアプリから独立させる。Webアプリは見た目や操作の確認時だけ起動する。エージェント接続中にMCPプロセスが動くことは許容する。

これは合意済みの製品方針であり、現在の画面モックがSQLite/MCPを実装済みという意味ではない。

## Rationale

検索・取得のためだけにブラウザとWeb開発サーバーを起動する必要をなくす。DB専用サーバーを常駐させず、低い運用負担でローカルの資料とコードを管理する。同時に、収集側の生成作業を移植先プロジェクトの作業文脈から分離する。

## Considered options

- IDを探すために毎回Webアプリを開く運用は、呼び出しの手間とメモリ面で優先しない。
- 別プロジェクトからMCPで新規収集・生成まで行う案は、実装作業が混ざるため採用しない。
- 完全な非常駐を目指すCLIのみの構成は、接続中のMCPプロセスを許容するため現時点では必要ない。

## Revisit when

複数PC・複数利用者での共有や、MCP待機中の実測メモリが許容範囲を超える場合に再検討する。
